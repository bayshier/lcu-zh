# Standalone integration adaptations

LCU launches the original @oai/cua-repl server, original Sky/native services and original Chrome provider from one selected official application. Compatibility uses official identity/signature where applicable, supported platform/architecture, runtime metadata, required files, and recognized original host layout; selected versions are reported rather than checked against repository app-version/component-hash allowlists. It adds only the host integration needed outside the ChatGPT desktop application. The API, descriptions, schemas and upstream instruction files remain unchanged.

## macOS Unicode text input: reason and removal criterion

**Reason.** The signed macOS helper types each character as one key of the active layout and skips, without an error, every character that has no such key: Korean syllables, emoji, and `ñ` on French AZERTY (observed; `ü`, a dead-key character there, is modelled, not observed). Original `paste` inserts the same text intact. Pasting a whole multi-line string loses key semantics instead: a trailing newline is inserted as text rather than submitting a chat box or form, and a Tab is inserted rather than acting as a key. The wrapper therefore keeps control characters on the original typing path and pastes whole only the chunks between them that contain a character above U+007F. No app, helper, schema, API or instruction file is changed, and no input implementation is added. Evidence and the live results are in [the Unicode input record](verification/macos-unicode-input-2026-10-12.md).

**Removal criterion.** No per-pair switch exists today. Re-test on the app/runtime pair in use by calling the original `typeText` directly through `js` with the routed strings (mixed Korean/ASCII, emoji, combining marks and `ñ` on AZERTY) and independent field readback, as the 2026-10-12 run did. When the unadapted helper preserves them, delete the routing and its tests and record the pair in the verification record. If a per-pair switch is wanted before then, it must be added as a `native_input` value in [tested-versions.json](../tested-versions.json) that `lcu/tested.mjs` accepts and the Sky wrapper honours, as the Linux one is. No app-version or runtime-version allowlist selects the routing. Tracked in [upstream workarounds](UPSTREAM-WORKAROUNDS.md).

## Linux window-targeted input: reason and removal criterion

**Reason.** The original Linux engine (`sky_linux`) sends window-targeted input with `XSendEvent`. GTK 4 handles pointer and keyboard input through XInput2 only, so GTK 4 windows ignore every such key, click, scroll and drag without an error, and Qt ignores scroll. Measured on ChatGPT 26.928.31416 (CUA 0.0.27) with LCU 0.8.2 against GTK 3, GTK 4 (a fixture and gnome-text-editor), Qt 5, Qt 6, Java Swing, Firefox, Chrome for Testing, Electron and a VTE terminal: only GTK 4 ignored keys, clicks, scroll and drag, and only Qt ignored scroll. Desktop-level calls (XTEST) worked everywhere, with identical delivered events at `window.x + x`, `window.y + y`. The wrapper therefore follows the Windows precedent of interposing on the Sky RPC channel (`nodeRepl.rpc('sky', ...)`) while the original service stays authoritative.

**Removal criterion.** Remove a toolkit from the translation when a tested ChatGPT app/runtime pair handles it natively. That is a per-pair switch: after the full gates pass for the pair with the translation off (the GTK 4 and Qt window-targeted tests, with the `LCU_LINUX_INPUT_TRANSLATION=off` controls turned into positive assertions), list `"native_input": ["gtk4"]` and/or `["qt-scroll"]` on that pair's entry in [tested-versions.json](../tested-versions.json). LCU then skips the translation for exactly that pair; untested versions stay translated. When every supported pair lists a toolkit, delete the wrapper and its tests.
