# Claude Code lifecycle boundary and manual probe

LCU currently registers the original MCP server and generated skill in Claude Code. It does **not** register a lifecycle hook. This is an explicit integration limit: the original CUA plugin calls its hidden `turn_ended` tool on `Stop`, `Interrupt`, and `SubagentStop`, passing both `session_id` and `turn_id`. The selected app's source is `plugins/openai-bundled/plugins/unified-computer-use/.codex-plugin/plugin.json`; LCU's adaptation is in `lcu/codex_hooks.py`.

Claude Code's official [hook reference](https://code.claude.com/docs/en/hooks), checked 2026-09-25, says `Stop` runs when the main agent finishes but **does not run on user interrupt**; API errors use `StopFailure`. `SessionEnd` runs when the whole session exits, with no per-turn interrupt reason. [MCP tool hooks](https://code.claude.com/docs/en/hooks#MCP-tool-hook-fields) can call an already-connected server and interpolate hook input. The documented [common hook input](https://code.claude.com/docs/en/hooks#common-input-fields) and [Stop input](https://code.claude.com/docs/en/hooks#stop-input) supply `session_id` but not `turn_id`. The [MessageDisplay input](https://code.claude.com/docs/en/hooks#messagedisplay-input) has `turn_id`, but fires only when assistant text is rendered and cannot identify every tool-only computer-use turn. The guarded CLI probe below confirmed that actual original MCP calls use LCU's synthetic connection ID pair rather than Claude's hook IDs. Installing a Stop hook with `${turn_id}` would assume an undocumented field and pass an ID pair that does not match the observed MCP requests. No documented ordinary-CLI event provides reliable cleanup immediately after a user interrupts a still-open session. These are limits of the reviewed hook contract and installed version, not a claim about every future Claude version. The installed Claude Code 2.1.204 native binary contains `MessageDisplay`, `StopFailure`, and `SessionEnd` event strings but no `UserInterrupt` string; the running-call probe below supplies the live event evidence.

The original Chrome `browser-service.mjs` is one concrete cleanup consumer: its `TurnEndedTracker` registers `addTurnEndedHandler`, records matching browser `session_id` and `turn_id` on extension/CDP/IAB requests, and invokes browser callbacks when that pair ends. The service throws if a browser request lacks either identifier. The Windows native pipe host is another lifecycle consumer: the pinned original `Wre.closeActiveTurn` matches that ID pair and closes the native helper. An installed LCU candidate proved that direct matching Stop and Interrupt calls remove helpers, while a stale Stop leaves a newer turn intact. Claude Code registration does not dispatch those calls on either normal completion or interruption. Linux/macOS native-only runs do not establish Windows behavior; Windows native and Chrome opt-in both lack Claude's correct per-turn cleanup.

The original MCP server advertises `turn_ended` and `js_add_node_module_dir` alongside `js` and `js_reset`. LCU's Codex registration applies the original host visibility policy. Claude's [CLI reference](https://code.claude.com/docs/en/cli-reference) says a bare `--disallowedTools` rule removes matching tools from model context; [settings](https://code.claude.com/docs/en/settings) supplies the corresponding `permissions.deny` list. LCU's focused Claude settings adapter implements the equivalent filter with exact deny rules for those two host-only names while preserving other settings. The guarded scripted-provider run below verified their absence from the actual model tool request.

The official [Claude Agent SDK](https://github.com/anthropics/claude-agent-sdk-typescript) has a V1 streaming `Query.interrupt()` control. An SDK launch adapter could own the interrupt decision, but it would be a separate headless program rather than the normal interactive `claude` CLI. It would also need an MCP bridge to stamp one turn ID across original `js` calls and forward images and elicitation. Anthropic's [SDK V2 interrupt issue](https://github.com/anthropics/claude-agent-sdk-typescript/issues/120) records that its preview session interface lacks `interrupt()`. No SDK adapter is shipped or claimed here. The user explicitly authorized the guarded interactive Claude launch for this check; the launcher guard was followed, and the SDK executable was not used.

## Prepared manual falsification

The probe writes only to a new private temporary project. It generates the selected app's full local skill in that project, registers an LCU MCP command there, installs the two exact host-only deny rules, and installs project-local hooks that log event names, session IDs, and any supplied turn or tool-use IDs. The preparation command never starts Claude, copies account credentials, records prompts, or changes personal Claude settings.

```sh
python3 tests/claude_lifecycle_probe.py prepare \
  --release /absolute/path/to/installed/lcu/current \
  --output /private/tmp/lcu-claude-lifecycle-probe
cd /private/tmp/lcu-claude-lifecycle-probe/project
# In the owner's interactive shell, intentionally start the guarded `clod` launcher.
```

Once Claude starts, confirm the project MCP and skill are visible. Give it this normal-completion task: “Read the local LCU skill. Use LCU's original `js` tool to evaluate `1+1` and then `2+2` in separate calls, and report both results. Do not use the desktop or browser.” After it finishes, inspect `../events.jsonl` for `PreToolUse`, `PostToolUse`, and `Stop` with one session ID.

Then give it this interrupt task: “Use LCU `js` to set `globalThis.lcuProbe = 7`, then in a separate `js` call wait for 30 seconds before reporting the value. Do not use the desktop or browser.” Once the waiting tool call starts, interrupt Claude using its normal interactive control. Inspect the new lines in `../events.jsonl`; any `Stop`, `StopFailure`, or other event that runs immediately on interrupt would change the source-only conclusion. The guarded local scripted-provider run below followed this sequence and recorded the installed version's behavior.

The recorder itself was checked with a synthetic hook payload: it wrote only `{"event":"Stop","session_id":"session-1"}` with file mode `0600`, discarding a supplied prompt and transcript path. `prepare` succeeded against the installed macOS LCU release at `/private/tmp/lcu-delivery-install/current` without launching Claude.

## Guarded normal CLI against a local scripted provider

A subsequent guarded, interactive Claude Code 2.1.204 run used an isolated home and configuration, the literal fake key `lcu-fixture-only`, and a loopback Anthropic-compatible fixture. The fixture supplied predetermined responses; **no Claude model generated these tool calls or answers**. The CLI used the same prepared project and the installed original LCU MCP binary, with no desktop or browser action. This is a host integration check, not a model-quality or end-to-end desktop claim.

The fixture's metadata-only request log first saw a request without tools during startup, then a `/v1/messages?beta=true` request with `mcp__lcu__js` and `mcp__lcu__js_reset` in the model-visible tool list. Neither `mcp__lcu__turn_ended` nor `mcp__lcu__js_add_node_module_dir` appeared. `/mcp` still listed all four server tools; the actual model request establishes that the two project deny rules filtered the host-only tools from model context in this installed CLI version.

The original `js` tool's first call returned its normal computer-use documentation. Later scripted calls in the same CLI session ran `nodeRepl.write(globalThis.lcuProbe = 2)` and `nodeRepl.write(globalThis.lcuProbe + 2)`; their actual MCP results were `2` and `4`. The fixture's final text was predetermined and is not evidence of those values. For normal completion, project hooks logged `PreToolUse` and `PostToolUse` for both tool-use IDs, then `MessageDisplay` and `Stop` under one Claude session ID. `PreToolUse` and `PostToolUse` supplied `tool_use_id` but no `turn_id`; `Stop` supplied only `session_id`, while `MessageDisplay` supplied a distinct `turn_id`.

With that original JavaScript runtime initialized, a scripted call set `globalThis.lcuProbe = 7` and entered a 30-second wait. Esc returned the ordinary CLI to its prompt during the wait. Immediately afterward, the only new hook line was `PreToolUse` for that call: there was no `PostToolUse`, `PostToolUseFailure`, `Stop`, `StopFailure`, or `SessionEnd` while the session stayed open. The CLI transcript marked the interrupted tool result as rejected. A later read from the same original runtime returned `7`, proving execution had entered the call before Esc; this was an interrupt of a running tool, not merely a denied permission prompt. A fixture dispatch mistake caused that read-only check to repeat after its first result; those extra checks carry no lifecycle inference. The CLI and fixture were then exited normally.

Finally, a sanitized JavaScript read of `nodeRepl.requestMeta` on an actual Claude-driven MCP call found `x-codex-turn-metadata` with a synthetic `lcu-…` session ID and a matching `…-connection` turn ID. These are the LCU connection fallback values. They differed from Claude's hook `session_id` and `MessageDisplay` `turn_id`. Thus the ordinary CLI did not supply the real Claude ID pair in the original MCP call, and a Stop hook cannot safely dispatch original `turn_ended` by copying its own `session_id` and a displayed turn ID. The installed CLI also emitted no hook at the observed user interrupt. Per-turn cleanup remains an explicit Claude integration gap. A supported solution would need a host surface that forwards a stable matching session/turn pair on each original MCP call and signals completion and interruption for that pair; no production proxy or inferred event is added here.
