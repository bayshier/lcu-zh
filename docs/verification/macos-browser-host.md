# macOS Chrome native-host seam

The locally installed ChatGPT macOS app (bundle version `10789`) contains the original Chrome plugin at `Contents/Resources/plugins/openai-bundled/plugins/chrome`. Its `scripts/installManifest.mjs` has SHA-256 `7891e11584097711195e2e8b36f2daecdcd762900f25fa7f28a78d7c9eb26bc1`. Source inspection shows that it selects `extension-host/macos/<arch>/ChatGPT for Chrome`, accepts `arm64` and `x64`, and writes per-user `com.openai.codexextension.json` native-messaging manifests for Chrome, Chromium, Chrome for Testing, Edge, Brave, Opera, and Vivaldi under `~/Library/Application Support`. The installed app actually contains only the ARM64 host binary (SHA-256 `aff232f3a4a5c26c1c5a198e6558b9138940e8a9b0aea9f5bb8679ace86c839b`). An x64 installation needs its own verified original x64 binary; this ARM64 installation cannot supply it.

`lcu browser install` copies that plugin from the selected app into a private user-owned directory because the original installer writes `extension-host-config.json` beside its binary. It invokes the original installer with the selected runtime paths, then replaces only manifests that point into that exact private copy with LCU's relay path. The relay selects the original macOS binary and preserves all native messages except the already authorized `agentRequestHeaderEnabled: false` capability reply. The installer does not install a browser or extension. It changes native-host registrations only when setup is explicitly invoked; tests use a disposable home and a fake original installer.

A read-only source check and a one-off run of that original installer with a copied plugin and disposable `HOME` produced eight per-user manifests and `extension-host-config.json`. Each manifest resolved to the copied original ARM64 host. The path was canonicalized through macOS's `/var` to `/private/var` symlink, which is why the LCU rewrite checks resolved paths. A separate disposable setup run invoked LCU's `install()` with a test release symlink to the locally installed app and the real bundled Node executable; all eight generated manifests pointed to the private LCU relay, and the original app remained unchanged. No browser or personal profile was opened.

The original installer has no website-origin approval setting. Its manifest's `allowed_origins` contains extension IDs, not websites. The original browser provider asks the MCP client for site approval through `elicitation/create`; prior Linux verification observed a fresh approval request for a new MCP service process. Therefore upfront website grants must be supplied by an explicit caller policy that handles the original scoped elicitation request, if such a policy is desired. Native-host setup does not grant sites, and this seam adds no default approval or new bypass.

This is source and unit-test evidence for the macOS host path. It is not a live macOS browser action or proof that the selected macOS app supplies the full standalone CUA runtime. The pinned Linux app's installer has a different SHA-256 (`868b088e078e73fc1eea5a81a04452758cbcc02723be9a3ae4d3825e7fa35fbe`); keep architecture and package provenance separate.
