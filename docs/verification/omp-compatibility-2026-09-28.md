# Oh-my-pi compatibility review, 2026-09-28

As of 2026-09-28, OMP's latest official release is [v18.4.1](https://github.com/can1357/oh-my-pi/releases/tag/v18.4.1). Its Darwin arm64 release binary was installed outside the user's profile and verified as Mach-O arm64 with SHA-256 `f5b9bb407e685f92f32e6c14d6dab64570d2a0c85a6a19d74fdce38c64e07d14`. Native OMP v18.4.1 RPC tests in isolated user profiles discovered the linked `lcu` skill. A fake-provider host test verified extension loading, first-request LCU tool presentation, and dispatch through the adapter. Project scope is rejected because OMP's local plugin-link CLI warns that `--scope` is ignored; setup must not label that write as project-scoped.

## LCU evidence

- Setup adds the `omp` harness using the shared Pi adapter and installs a generated package with OMP's native `omp.extensions` manifest through the profile-scoped `omp plugin link` command. OMP project scope is not supported.
- The generated wrapper imports the shared adapter by a relative path so OMP's compiled loader can resolve its transitive package graph. It enables eager connection and OMP's `essential` presentation for LCU tools; Pi tool registration keeps its existing behavior.
- The generated package includes the full LCU skill under `skills/lcu/`. OMP's actual RPC command list reports it with `source: "skill"`.
- [Current host verification](latest-standalone-harness-2026-09-27.md) covers Pi 0.87.1; it is separate from the OMP v18.4.1 fixtures described here.

## Upstream evidence

The current release and behavior were checked against the official [v18.4.1 release](https://github.com/can1357/oh-my-pi/releases/tag/v18.4.1) and version-pinned primary sources. Earlier extension-loading details were cross-checked on upstream `main`.

- [Extension loading](https://github.com/can1357/oh-my-pi/blob/v18.4.1/docs/extension-loading.md) documents `pi.extensions` manifest compatibility, package extension discovery, and explicit `--extension`/`-e` paths. Plugin packages can use `omp.extensions`; OMP also scans linked plugin packages' conventional `skills/` directory.
- [Extension API types](https://github.com/can1357/oh-my-pi/blob/v18.4.1/packages/coding-agent/src/extensibility/extensions/types.ts) expose the same five tool execution arguments used by LCU, define `before_agent_start.systemPrompt` and its replacement as `string[]`, and default extension tools to `loadMode: "discoverable"`. LCU's two core tools opt into `loadMode: "essential"` for OMP so the model sees them in the initial tool list.
- [Extension runner](https://github.com/can1357/oh-my-pi/blob/v18.4.1/packages/coding-agent/src/extensibility/extensions/runner.ts) passes the prompt array to `before_agent_start` handlers and accepts a returned string by wrapping it in an array. LCU now appends its instructions as one new array entry for OMP and keeps the original string behavior for Pi.
- The [compiled Pi compatibility loader](https://github.com/can1357/oh-my-pi/blob/v18.4.1/packages/coding-agent/src/extensibility/plugins/legacy-pi-compat.ts) traverses relative imports to resolve transitive dependencies. A `file://` wrapper failed SDK resolution in OMP 18.1.6; the relative import passed the real host test.
- [Extension loader](https://github.com/can1357/oh-my-pi/blob/v18.4.1/packages/coding-agent/src/extensibility/extensions/loader.ts) records event handlers directly and notifies listeners when tools are registered. This supports tools registered during `before_agent_start`.
- [Plugin manager installer plumbing](https://github.com/can1357/oh-my-pi/blob/v18.4.1/docs/plugin-manager-installer-plumbing.md) describes linked plugin paths, enabled-plugin discovery, extension manifests, and conventional skill discovery. [Plugin CLI](https://github.com/can1357/oh-my-pi/blob/v18.4.1/packages/coding-agent/src/commands/plugin.ts) exposes `omp plugin link --scope user|project <path>`; `user` is the default.
- The version-pinned [v18.4.1 plugin-link CLI handler](https://github.com/can1357/oh-my-pi/blob/v18.4.1/packages/coding-agent/src/cli/plugin-cli.ts) calls `manager.link(paths[0])`; the handler does not pass `--scope`, and the local-install path explicitly warns that this flag is ignored. LCU refuses project scope rather than writing into a profile behind the user's back.
- The v18.4.1 [model configuration reference](https://github.com/can1357/oh-my-pi/blob/v18.4.1/docs/models.md) documents per-model `compat.supportsDeveloperRole`. The actual-flow runner disables developer-role messages for its local OpenAI-compatible Z.ai proxy, which rejected that role with HTTP 400.
- [Extension documentation](https://github.com/can1357/oh-my-pi/blob/v18.4.1/docs/extensions.md) documents `ctx.ui.select()` and session/agent lifecycle events. OMP defines `session_shutdown`, but its documented SIGTERM/SIGHUP/uncaught-exit path skips session disposal and that event (see [upstream issue #4055](https://github.com/can1357/oh-my-pi/issues/4055)).

## Verification and limits

Note (2026-10-05): the prompt handling below describes what was observed on 2026-09-28. The shared adapter has since changed for Pi hosts that provide `event.systemPromptOptions`: it appends the instructions to `systemPromptOptions.appendSystemPrompt` and returns no `systemPrompt`. The array/string return path described here is kept when `systemPromptOptions` is absent, which includes OMP (its v18.4.1 `before_agent_start` event has only `prompt`, `images` and `systemPrompt: string[]`). The change is covered by unit tests and Pi source reading, not live Pi verification.

OMP and Pi share the adapter's relevant tool callback, `registerTool`, command, UI selection, elicitation, and lifecycle surfaces. OMP's `before_agent_start` prompt is an array; LCU now appends without flattening existing blocks. `adapters/test/omp.test.mjs` models that host shape and verifies prompt preservation, dynamic tool registration, result forwarding, and normal `Stop` cleanup through the original stdio MCP fixture. Existing Pi tests continue to cover approval decisions and cancellation.

The actual-model GTK flow passed on OMP v18.4.1 (`omp/18.4.1`, Darwin arm64 binary SHA-256 `f5b9bb407e685f92f32e6c14d6dab64570d2a0c85a6a19d74fdce38c64e07d14`). OMP ran on the host in a temporary HOME and profile, linked the generated Linux LCU skill, and used `openai/glm-5.3-flash` through a host-loopback credential-injecting proxy. The existing provider credential stayed in the host proxy's memory; it was not copied into the OMP profile or fixture. The model received only the synthetic GTK fixture, called the original LCU tools, and saved marker `omp-lcu-031538f03c23` in `Target.txt`. The independent Linux ARM64 container oracle found that exact value and confirmed `Other.txt` absent.

The isolated fixture used the final Linux ARM64 archive at `.verification/arm64.5fnpEe`, OpenAI desktop app `26.915.31945`, and original runtime `0.0.16`. The container had network access disabled and exposed only the generated `LCU Target` and `LCU Other` GTK windows. This verifies a model-directed Linux GTK action through OMP and the original LCU runtime. That GTK run alone does not verify macOS desktop behavior, browser actions, or interactive approval UI.

`tests/omp_approval_ui.py` subsequently exercised the installed OMP v18.4.1 interactive TUI in nine fresh profiles. A local scripted provider requested an LCU tool, the official MCP SDK fixture elicited approval, and the test selected the rendered OMP menu with PTY key input. Native once/session/always, explicit decline, Escape cancellation, a session-only request with no permanent option, and browser-origin accept/decline/Escape all passed. Each case checked the exact returned MCP response and observed the adapter's normal `turn_ended` cleanup. This proves the actual OMP UI-to-adapter path, independently of model reasoning; the generated MCP fixture does not prove that the original runtime persists grants.

Reproduce with `python3 tests/omp_approval_ui.py --omp /absolute/path/to/omp --evidence /path/outside/the/repository/omp-ui`. The fixture seeds only its own profile's provider and setup state: official OMP [setup settings](https://github.com/can1357/oh-my-pi/blob/v18.4.1/packages/coding-agent/src/modes/settings.ts) and [setup version](https://github.com/can1357/oh-my-pi/blob/v18.4.1/packages/tui/src/setup/setup-version.ts) define `setupVersion: 2`. It does not read personal OMP configuration, use a provider credential, or access a desktop.

Reproduce actual GTK verification by setting `OMP_BIN`, `OMP_FIXTURE_CONTAINER`, `OMP_MODEL`, `OMP_PROXY_BASE_URL`, and `LCU_DOCKER_HOST`, then running `python3 tests/omp_real_gtk.py --evidence-file /path/outside/the/repository/evidence.json`. The script requires a prestarted network-none GTK container and a host-local proxy that injects credentials without exposing them to the script. The evidence JSON includes OMP output, which may contain original runtime instructions; keep it outside the repository. Reproduce registration with `OMP_BIN=/absolute/path/to/omp python3 tests/omp_registration.py`; it checks two isolated user profiles and verifies that setup rejects project scope. Reproduce fake-provider prompt/tool/cleanup verification with `OMP_BIN=/absolute/path/to/omp python3 tests/omp_host.py`. The host fixture observed a two-second `session_shutdown` hook timeout after successful matching `Stop` cleanup; shutdown completion is not claimed.

The subsequent clean commit snapshot passed 199 Python tests, the offline installation and GTK desktop suite, and 27 adapter tests (8 optional skips). See the [combined reproduction and final gate record](harness-desktop-flows-2026-09-28.md) for the snapshot boundary and unrelated working-tree test failure.
