# LCU 0.8.6

This release fixes five review findings in the Linux window-targeted input translation. It adds no new harness verification claims and no new tested app pairs; Windows remains deferred.

## Changes

- **Overlays no longer receive translated pointer input.** A notification, tooltip or override-redirect popup could cover a focused GTK 4 target (activation is skipped for a focused window, the bounds check passes, and the desktop-level click follows normal pointer routing onto the overlay). Immediately before a translated click, double click, scroll, drag start or move, LCU asks the X server which mapped window is at the converted point and requires it to be the target or one of its descendants; otherwise the call fails with an error and sends nothing. The query only reads and honors input shapes. The documentation no longer says the target "is raised".
- **A hung original call can no longer block input forever.** Every call the queue makes to the original service is bounded (30 seconds). On a timeout LCU stops the trusted worker, which ends the original engine process so the call cannot act late, fails the call, and refuses queued calls without sending them; `node_repl` starts a fresh worker for the next request.
- **The X server must share LCU's PID namespace.** Before trusting an X-Resource process id, the helper checks that the server's record of the helper's own client equals its `getpid()`; otherwise it fails closed (LCU in a child PID namespace with the X server outside could previously be fooled by colliding ids).
- **An unreadable `/proc/self/ns/pid` now fails closed** instead of open.
- **Untranslated requests no longer start the X helper.** The toolkit and method are checked first, so a Qt key, a Chromium window or a hidden window pays nothing; a translated request costs one short `python3` start for the identity and one for the pointer check.
- `SYSTEM_PACKAGES` is unchanged (`libxres1` and `python3` were already required). `LCU_LINUX_INPUT_TRANSLATION=off` and the per-pair `native_input` switch are unchanged. See [Linux window-targeted input](../ADAPTERS.md#linux-window-targeted-input) and the [verification note](../verification/linux-input-translation-2026-10-02.md#086-overlays-hung-calls-namespace-proof).

## Gates

- `tests/run.sh linux/arm64` (native, original sandbox required in the read-only gate, with the negative control and the stricter-host-profile check) and `tests/run.sh linux/amd64` (emulated; the sandbox cannot be required there) passed against the official ChatGPT 26.915.31945 (the pinned package): 325 Python tests (3 environment skips), offline in-place installation, agent registration, the exported MCP contract, the original GTK desktop suite, the adapter-path suite, the GTK 4 window-targeted suite (now with a real override-redirect overlay over the focused target: click, double click, move, scroll and drag refused, nothing reaching the overlay, clicks beside it and after it left still working), the controls suite, the new hung-engine suite (the real `sky_linux` process stopped with SIGSTOP: the call failed after 3 s, no late key reached the entry, the engine process was replaced and the next request worked) and the read-only mount gate. The ChatGPT 26.928.31416 packages were not re-run for this release because neither `.deb` was available locally and nothing outside `tests/run.sh` was downloaded; its pairs in `tested-versions.json` still cite the 0.8.0 evidence. 26.915.31945 has no `key_down`/`key_up`, so the pass-through checks did not run.
- Observed on the hung call: the caller received either LCU's own error (`The original Linux input service did not answer "press_key" within 3 s ...`) or, when the worker's exit won the race with the reply, `node_repl`'s `trusted Node process exited unexpectedly; kernel reset, rerun your request`. Both mean the worker and engine were replaced; the JavaScript kernel's bindings are reset, so a caller re-creates what it needs.
- Native x86-64: on an Ubuntu 26.04 host with native Docker (KVM, 16 cores), the release build of the x64 archive passed the same read-only mount gate with the desktop suites as the unprivileged account, the original sandbox required, against the pinned package (the host's full `tests/run.sh` was not used, so its 325 Python tests did not run there; the earlier attempts failed in the gate itself, not in LCU: that unit test's timing assertion, a pseudo-terminal drain count of 1046272 against 1048576, and the throwaway directory's owner-only permissions, which the unprivileged test account could not read). The run used a temporary directory and a throwaway image, all removed; no installed application, VM, `~/.silo` or `~/.microsandbox` state on that host was touched.
- `adapters/test/linux-sky-service.test.mjs`: 32 in-memory tests (9 new; 7 of them fail against the 0.8.5 logic, and the hung-call ones only end through the test timeout), and `node --test adapters/test/*.test.mjs` passes (68 passed, 8 environment skips, 0 failed).
- The cross-PID-namespace refusal was exercised against a real Xvfb as root with `unshare --pid` on both architectures (native arm64 and native x86-64 containers): the helper reported the owning process from the same namespace and nothing from a child namespace while its `at` query still worked. The gates themselves run the desktop suites unprivileged, where `tests/linux_xres_namespace.py` skips that half with a notice.
- The macOS archive was built; no desktop action ran on macOS and no model-driven run was made for this release. Fractional scaling, other window managers, real notification daemons or popup menus (the overlay is a fixture window), real Chrome or Electron applications, and a window from a genuinely remote X client were not exercised.
