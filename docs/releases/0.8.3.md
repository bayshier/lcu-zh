# LCU 0.8.3

This release makes window-targeted keys, clicks, scroll and drag work on GTK 4 windows on Linux (and scroll on Qt), documents the sandbox default's security consequence, and fixes where the opt-out variables must be set. It adds no new harness verification claims and no new tested app pairs; Windows remains deferred.

## Changes

- **Linux: window-targeted input reaches GTK 4 and Qt scroll.** The original engine sends window-targeted `pressKey`, coordinate `click`, `scroll`, `drag` and pointer moves with `XSendEvent`. GTK 4 (XInput2 only) ignored every one of them without an error, and Qt ignored scroll; GTK 3, Firefox, Chromium, Electron and terminals were fine. LCU now sits on the Sky RPC channel, as the Windows wrapper does, and for a GTK 4 window (identified by `_NET_WM_PID` and `libgtk-4` in the process maps) re-issues those calls through the engine's own `activate_window` and desktop-level calls with window-relative coordinates converted to desktop coordinates; for Qt it does so for scroll only. A GTK 4 window with a modal dialog gets the input at the dialog. Everything else is untouched: other toolkits, `typeText`, `paste`, AT-SPI element actions, Chromium and Electron processes, and a window that is off screen, minimized or not listed (the engine reports its normal result). The visible cost is that the translated target is raised and focused and the real pointer moves. `LCU_LINUX_INPUT_TRANSLATION=off` restores the original behavior, and a tested app/runtime pair can switch the translation off per toolkit with `native_input` in `tested-versions.json` once its own gates pass without it. No pair does yet. See [Linux window-targeted input](../ADAPTERS.md#linux-window-targeted-input), the [adaptation record](../STANDALONE-ADAPTATIONS.md#linux-window-targeted-input-reason-and-removal-criterion) and the [measurements](../verification/linux-input-translation-2026-10-02.md).
- **Linux sandbox default: kept, now documented plainly.** 0.8.2's default stays: when the host sends no sandbox state, `lcu` supplies Codex's disabled one so computer use reaches the desktop as it does on macOS. The consequence is that the original `node_repl` JavaScript kernel then runs without the sandbox: code the model writes in `js` calls can write files outside the workspace, use the network and start subprocesses as your account. The reason is that the current Linux runtime's network-off seccomp filter also blocks the X11 socket, while macOS reaches a signed helper over an allowed pipe and is unaffected. A host that sends its own sandbox state keeps it, and `LCU_NODE_REPL_SANDBOX=host` opts out. The Codex relay does not currently forward Codex's own sandbox mode, so `read-only` or `workspace-write` in Codex does not restrict the kernel; this will be revisited when OpenAI's runtime gains a socket exception. See [Linux sandbox state](../ADAPTERS.md#linux-sandbox-state) and the [installation notes](../INSTALLATION.md#linux-sandbox-and-input-notes).
- **Opt-out variables and Codex.** Codex filters the environment of the MCP servers it starts and LCU registers no `env_vars`, so `LCU_NODE_REPL_SANDBOX=host codex` never reached LCU. Set it, and `LCU_LINUX_INPUT_TRANSLATION`, under `[mcp_servers.lcu.env]` in the Codex configuration (rerun-safe only until the next `lcu setup --agent codex`, which replaces that table). The installation guide lists the equivalent for Claude Code, Pi, Oh My Pi, Hermes and generic clients. `tests/codex_mcp_env.py` reproduces the filtering with an isolated Codex CLI. `lcu setup` does not write these entries.
- **GTK 4 `typeText` is engine dependent.** 0.8.2's notes and the installation guide said `typeText` works on GTK 4. ChatGPT 26.928.31416 inserts through AT-SPI (in some runs the first call to a freshly started app inserted nothing and later calls inserted); 26.915.31945 returns success without inserting. Where it inserts nothing, activate the window and use the desktop-level `sky.type_text`. The installation guide is corrected, and the 0.8.2 notes carry a correction note.
- **Tests.** New GTK 4 oracle tests for window-targeted keys, chords, held modifiers, click, scroll, drag, a modal dialog and the opt-out; a controls suite proving GTK 3, a core-event X11 window, Qt keys and click and a Chromium-like process stay on the original path with the focused window unchanged, and that Qt scroll is translated (with a translation-off control); window-targeted GTK 4 keys and click through every adapter path; unit tests for the wrapper registration, the opt-out and the per-pair switch. The adapter-path suite now asserts that `turn_ended` succeeds and then makes real computer-use calls (window list, state, a persisted sentinel) without sandbox metadata, instead of `6 * 7`.

## Gates

- `tests/run.sh` passed in disposable Linux ARM64 (native) containers against the official ChatGPT 26.928.31416 and 26.915.31945 packages, and in AMD64 (emulated) containers against the same two: 323 Python tests, offline in-place installation, agent registration, the exported MCP contract, the original GTK desktop suite with its independent save oracle, the adapter-path suite (bare client, Codex relay, Claude relay, shared Pi/Oh My Pi client, Hermes bridge, no sandbox metadata, now also window-targeted GTK 4 keys and click and a real post-`turn_ended` call), the GTK 4 window-targeted suite, the controls suite, and the read-only mount gate. The read-only gate on ARM64 ran with bubblewrap allowed (`seccomp=unconfined`, `apparmor=unconfined`, `SYS_ADMIN`) and required the original sandbox to be active, with the negative control and the stricter-host-profile check. Under emulation bubblewrap cannot start, so the sandbox could not be required on AMD64 there.
- Native x86-64: on an Ubuntu 24.04 host with native Docker, the same commit's release build of the x64 archive ran the desktop suite (GTK suite, adapter paths with the sandbox required, GTK 4 window-targeted and controls suites) as the unprivileged account against both packages with the same container flags; both passed. As for 0.8.2, that host's full `tests/run.sh` was not used. The run used a temporary directory and a throwaway image, both removed; no installed application, VM or user data on that host was touched.
- The new tests are not vacuous: with `LCU_LINUX_INPUT_TRANSLATION=off` the same window-targeted GTK 4 keys and click, and the Qt scroll, change nothing on both app versions, and the focused window stays the same. The first gate run found two test races (a window listing that raced a closing dialog, and Qt taking focus itself on a click); both were test fixes, not behavior changes. 26.915.31945 has no `key_down`/`key_up`, so the held-modifier check runs only on 26.928.31416.
- The adapter checks passed 36 tests with 8 environment skips on macOS. `tests/codex_mcp_env.py` ran against Codex CLI 0.159.1 in an isolated home with a scripted provider: a variable set in the Codex process environment did not reach the MCP server (directly or behind the relay), and one under `[mcp_servers.lcu.env]` did.
- No model-driven run was made and no desktop action ran on macOS for this release; the macOS archive installed with `--offline --runtime-only` into a disposable prefix (`--version`, `status --json`). Setup and the harness fixtures ran only in disposable containers and isolated homes. The Claude Code, Pi, Oh My Pi and Hermes environment locations in the installation guide follow from their adapters' code (the shared client starts `lcu` with the harness process environment) and Claude Code's documented MCP `env`; they were not exercised live. Fractional scaling, other window managers and real Chrome or Electron applications were not exercised.
