# LCU 0.8.5

This release shrinks and hardens the Linux window-targeted input translation after a second review of 0.8.4. It adds no new harness verification claims and no new tested app pairs; Windows remains deferred.

## Changes

- **Held keys are no longer translated.** `key_down` and `key_up` now always go to the original service unchanged, and the hold bookkeeping is gone. 0.8.4's claim that translated holds were "always released" was wrong (see the correction in the [0.8.4 notes](0.8.4.md)): partial chord releases, key aliases such as `Shift` and `Shift_L`, a failed release and turn cleanup could all leave a modifier held. On a GTK 4 window a held key now behaves as in the original engine, which delivers it with `XSendEvent` and so is ignored. To hold a key for a GTK 4 window, activate it and use the desktop-level `key_down`/`key_up` (no `window`). `press_key` (atomic chords, with the original engine owning the whole chord), `click` (including double), `scroll`, `drag` and `move` stay translated for GTK 4, and `scroll` for Qt.
- **Everything that can change focus or input runs through one queue.** `activate_window`, desktop-level input, window-targeted input of every kind, `typeText`, pass-through fallbacks and untranslated calls are serialized with translated requests, so nothing interleaves between a translated request's final focus check and its input (an `activate_window` of another window could previously move a key to that window). Read-only calls (`list_windows`, `list_apps`, `get_screenshot`, `get_window_state`) bypass the queue. The focus is still verified immediately before the desktop-level call.
- **Window ownership comes from the X server.** `_NET_WM_PID` is the client's own claim in its own PID namespace, so a client sharing the X socket from another namespace (Flatpak, containers) could advertise an id that collided with an unrelated local process. LCU now asks the X server (X-Resource `XResQueryClientIds` with the PID mask, the `SO_PEERCRED` id; nothing for a remote client) and translates only when it equals `_NET_WM_PID`, the machine is this host and the process shares LCU's PID namespace. Anything else, or an unavailable query, fails closed to the original behavior.
- **New system package: `libxres1`** (X.org X-Resource client library, about 7 kB, Ubuntu `main`) was added to the installer's `SYSTEM_PACKAGES`. Silo's image needs it as well; without it, or without `python3`, GTK 4 and Qt windows behave as in the original engine.
- `LCU_LINUX_INPUT_TRANSLATION=off` and the per-pair `native_input` switch are unchanged. See [Linux window-targeted input](../ADAPTERS.md#linux-window-targeted-input) and the [verification note](../verification/linux-input-translation-2026-10-02.md#085-smaller-translation-authoritative-process-identity).

## Gates

- `tests/run.sh` passed in disposable Linux ARM64 (native) containers against the official ChatGPT 26.915.31945 (the pinned package) and 26.928.31416 packages, and in AMD64 (emulated) containers against the same two: 325 Python tests (3 environment skips), offline in-place installation, agent registration, the exported MCP contract, the original GTK desktop suite with its independent save oracle, the adapter-path suite, the GTK 4 window-targeted suite (now with `key_down`/`key_up` passed through unchanged, an `activate_window` racing a translated key in both orders and a desktop-level key issued together with a translated one), the controls suite, and the read-only mount gate. The ARM64 read-only gate ran with bubblewrap allowed and required the original sandbox to be active, with the negative control and the stricter-host-profile check; under emulation bubblewrap cannot start, so the sandbox could not be required on AMD64. 26.915.31945 has no `key_down`/`key_up`, so the pass-through checks run only against 26.928.31416. The first ARM64 run against 26.928.31416 failed one unrelated host-harness unit test (`test_macos_acceptance`, a pseudo-terminal drain count of 1044223 against 1048576, a timing assertion); the unchanged rerun passed.
- Native x86-64: on an Ubuntu host with native Docker, the release build of the x64 archive ran the read-only mount gate with the original sandbox required (the desktop suites as the unprivileged account) against both packages; both passed. As for 0.8.3 and 0.8.4, that host's full `tests/run.sh` was not used. The run used a temporary directory and a throwaway image and volumes, all removed; no installed application, VM or user data on that host was touched.
- The wrapper logic is covered by `adapters/test/linux-sky-service.test.mjs` (23 in-memory tests against a fake desktop that follows the original engine's chord semantics; 6 fail against the 0.8.4 logic) and `node --test adapters/test/*.test.mjs` passes (59 passed, 8 environment skips, 0 failed). The X-Resource query was also exercised directly against a real Xvfb in an Ubuntu 24.04 container: it returned the connecting process's id, and failed closed without `libxres1`.
- The macOS archive was built; no desktop action ran on macOS and no model-driven run was made for this release. Fractional scaling, other window managers, real Chrome or Electron applications, and a window from a genuinely remote or other-PID-namespace X client were not exercised; those rules are covered only by the in-memory tests. A Silo-like guest (Xvfb run as the same user by the desktop service) is the same shape as the gate's Xvfb fixtures, where the translated GTK 4 suite passed.
