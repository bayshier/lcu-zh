# Dependency provenance

The official desktop app must already be installed; LCU never downloads or installs it. Selection does not use repository app-version, runtime-version, or component-hash allowlists. macOS validates the official bundle/team identity and signatures, supported arm64 architecture, runtime platform/architecture, required files, and a recognized original Codex CLI/code-mode-host pair, then reuses the app in place. The current app check accepted ChatGPT `26.924.22138` with CUA runtime `0.0.24/20260924074400-f52ea85e2a98`; see [current macOS verification](verification/macos-current-app-2026-09-26.md). Linux selection uses the runtime manifest, architecture, structural checks, and the observed app version, then uses the installed app in place. Windows selection validates the registered official Store package identity, publisher/signature, architecture, and required structure, then records a source-derived inventory for the private copy. This policy description adds no new Windows live verification or support claim.

Historical Windows source specimen: the inspected Store MSIX had SHA-256 `9892383820c5505997456bde8385810afadd6076ae7fff9e3835a48ca0555c98`. Its `app/resources/app.asar` member `.vite/build/main-BR_2NHW6.js` had SHA-256 `1f2b91cf92fc023fb2fa41e1c1d03698fa6e37354ecd07dd0cebd21337607b08`; byte range `[155346,165208)` was the original native-pipe host factory, which that build named `Wre` (SHA-256 `3dae7a2bb89573e78dff25715efaf44dadbe7a7376c9243987d18d43b5f05247`). These hashes describe inspected source evidence, not the current app-selection allowlist. The Windows installer validates the selected app structure, extracts the required original host members (located by structure, see below), and records the complete source-derived inventory for its private copy. A thin entry starts and disposes the host outside the original sandboxed Node REPL. The original helper, Sky service, pipe protocol, approval forwarding and CUA API stay unchanged; none of those extracted bytes enters Git or a thin archive.

Native-pipe host layout (issue #13). Minified names change between builds, so LCU never selects the host by name. `lcu/windows_host_analyze.cjs` parses each `.vite/build/main*.js` and requires exactly one top-level function declaration (sync or async) whose first parameter is an object pattern naming `codexCliPath`, `nativePipeDirectory`, `windowsHelperPath` and `windowsHelperTransportModulePath`, and whose source mentions `closeActiveTurn`; zero or several matches stop the install. It then computes the scope-correct transitive closure of the bundle's top-level declarations that factory needs, plus the module-level `require` bindings they use and the top-level statements made only of assignments to a needed binding or a property path of it (`x=interop(x)`, `x.y=1,x.n++`), and writes those declarations verbatim and in their original order, followed by `module.exports = <factory>`, as one generated module beside the original main bundle's directory. It stops on Electron, a native module, an unresolved free identifier (anything neither bundle-declared nor a Node global), `eval`, a `require` that is not a call with a literal specifier or a binding named `require` or `eval`, a binding or property that load-time code outside the closure assigns, or a static dependency that is not a Node built-in or a relative file inside the archive. Any other top-level statement (a registering or mutating call, a guarded block, a loop) that references a needed binding the app declares itself is carried verbatim, in order, with its own dependencies under the same refusals. A statement that touches needed bindings only through imported module namespaces (a call into the zod or logger chunk, or a Node built-in, with its result discarded) is not carried, because its effects are inside modules the installer copies verbatim and carrying it would drag in unrelated chunks (in the macOS bundle it would reach the Electron-bound bootstrap chunk); the generated module's header counts them (7 in the macOS `26.930.21537` bundle: zod schema constructions, a logger registration and a property read). The installer copies exactly the files reached by walking the relative `require` graph from that module, resolving specifiers in Node's order (exact file, `.js`, `.json`, `.node`, directory `index`; a trailing slash means a directory) and stopping on a package directory. In the macOS ChatGPT `26.930.21537` bundle, the same release train as Windows `26.930.7945.0`, the factory is a 1,969-character async function that depends on about 38 top-level declarations; see [the structural extraction record](verification/windows-host-structure-2026-10-06.md). That record is a macOS bundle check and makes no Windows live claim.

Vendored parser. `lcu/vendor/acorn/acorn.js` is acorn 8.18.0 (MIT), the single-file CommonJS build from the npm tarball `https://registry.npmjs.org/acorn/-/acorn-8.18.0.tgz` (npm integrity `sha512-lGq+9yr1/GuAWaVYIHRjvvySG5/4VfKIvC8EWxStPdcDh/Ka7FG3twP6v4d5BkravUilhIAsG4Qj83t02LWUPQ==`, verified against the registry's `dist.integrity` after `npm pack`). `dist/acorn.js` has SHA-256 `fc3ed7b81e58464715d0291402892f22c3d86ea75302645a330390f85d8015c9` and the package `LICENSE` (copied beside it) has SHA-256 `76a876cf886ff9be2a8b5e2e86514fed06223c8c9f0c1e9ee9606e93841e00b7`. Neither file is modified. It exists because the structural check needs a real JavaScript parser and neither Python's standard library nor the installer toolchain has one; it runs in a copy of the application's own `node.exe` (the protected Store directory refuses direct execution), parses the app's code and never evaluates it. The build copies it into the Windows archive with its licence; LCU's MIT licence does not relicense it.

The original app's `Noe` handler (names are that build's minified identifiers) calls the host's `closeActiveTurn({sessionId,turnId})` directly on app-server `turn/completed`; the standalone Node REPL and host are separate processes. LCU's Windows trusted-service wrapper forwards `nodeRepl.rpc('sky',...)` to the unchanged original Sky service, registers the original `addTurnEndedHandler`, and uses the original `nodeRepl.nativePipe` facility to send only real session/turn IDs over a random private lifetime pipe. The host calls unchanged `closeActiveTurn`; this signal neither routes CUA methods nor grants access. Installed candidates listed a live Notepad window and saved exact Unicode text to an existing file with an independent byte oracle. A matching Stop removed its helper, a stale Stop left a newer turn's helper intact, a matching Interrupt removed that helper, and MCP shutdown removed a third helper. The original `turn_ended` tool returned `{}` even when an earlier callback failed, so this conclusion rests on the independent helper-state oracle. See [Windows source evidence](verification/windows-source.md) for the guest boundary.

The historical Linux source package inspected for the earlier host tests was ChatGPT `26.915.31945`, with CUA runtime `0.0.16/20260915001755-492f19756c31`. `runtime.lock.json` retains that package URL template, architecture-specific SHA-256 digests, and critical-file hashes for independently managed development/test inputs. These records neither authorize installer acquisition nor select app compatibility. LCU setup accepts an already-installed app at `/usr/lib/chatgpt` or `--existing-app PATH`; `--app-package` is retired. The selected app is validated in place by architecture, runtime manifest, required structure, recognized host layout, and ownership/writability of the executables and their directories (it must be changeable only by root and the desktop account). LCU does not copy it, authenticate its content, or inventory its tree on Linux; it records the observed version and runtime and warns when they later change.

The inspected .deb control metadata says Package=chatgpt, Version=26.915.31945, with Architecture=arm64 or amd64. The historical app lived at usr/lib/chatgpt and contained the unchanged resources/cua_node runtime, resources/codex and resources/codex-code-mode-host, plugin tree, Electron application and original notices. LCU copies the complete selected installed app under a managed prefix and records the observed version/runtime plus a deterministic full-tree inventory digest. It does not run package maintainer scripts or register the app with apt.

The inspected package post-install script writes an OpenAI apt key/source and loads an AppArmor profile. That profile is bound to /usr/lib/chatgpt/ChatGPT, the original Electron UI executable, and grants userns to it. LCU launches the selected app's Node/REPL directly, without running that post-install script. Ubuntu 24.04.5 ARM64 and x86-64 guests with AppArmor active passed installed native fixtures and no-sign-in Chrome actions using LCU's relay; the x86-64 guest ran under KVM on physical AMD hardware. Process sampling found Node/REPL `unconfined`, Chrome and the extension host `chrome (unconfined)`, and nonblocking `bwrap` capability denials. Chrome launched without `--no-sandbox`. See the [exact verification record](verification/installed-app-2026-09-23.md).

The original Chrome provider and native messaging host come from `resources/plugins/openai-bundled/plugins/chrome` in this same installed app. Its `scripts/installManifest.mjs` registers native messaging; LCU copies that plugin to the target account's writable data directory during browser setup, runs the original installer there, and points the account's manifest at LCU's small relay. The relay locally enables the official extension's agent request label. The original `docs/chrome-troubleshooting.md` lines 31–38 directs a missing-extension user to the selected browser's exact `storeUrl` in `scripts/extension-ids.json` and requires permission before opening the store or management page. It provides no silent Web Store installation action; the desktop user must confirm installation or enablement in the browser. LCU prints the same official store link and preserves that browser confirmation boundary. [OpenAI's extension documentation](https://learn.chatgpt.com/docs/chrome-extension) gives its supported setup flow. [Google's Chrome Linux guide](https://support.google.com/chrome/answer/95346?hl=en) lists both x86-64 and ARM64 packages. Extension discovery alone does not prove browser action.

The shared harness client uses `@modelcontextprotocol/sdk` 1.30.0, pinned in `adapters/package-lock.json`; it delegates MCP protocol behavior to that SDK. Pi and OMP supply their extension host. Hermes supplies its native Python plugin host; LCU's private Node bridge uses the same MCP SDK client. LCU does not bundle or install these harnesses. OMP and Hermes setup packages include original instruction references generated only on the destination machine; release archives contain just LCU's plugin and bridge source.

The build fetches separately pinned third-party agent registration tools defined in scripts/agent-tools/package-lock.json. Their temporary build Node is discarded; setup uses the selected official app Node. These tools and LCU code may appear in a thin archive, subject to their own licences. Original OpenAI app binaries, runtime packages, documents and generated fragments must not. The copied full-bundle source was removed from the working tree. The full-copy commit was removed from the new local main lineage, and its remote feature branch was deleted.
